# ClientPulse

Freelancer/agency SaaS: Laravel API + Next.js frontend. Dutch freelancers manage clients, log project
hours, and generate invoices with localized payment links.

## Layout: two independent apps, no workspace tooling

- `backend/` — Laravel 13 (`laravel/framework ^13.17`), own `composer.json` / `package.json` / lockfiles
- `frontend/` — Next.js 16 App Router, own `package.json` / lockfile
- No root package manifest and no workspaces. There *is* a root `docker-compose.yml` and a
  root `.env.example`; the root `.env` they copy from is gitignored and configures Compose
  only, not Laravel. Run `composer` and `npm` from inside each directory. No CI, no active
  git hooks.
- Single branch `master`. Commits follow Conventional Commits (`chore: add README and install Laravel Boost`).
- The two apps do not talk to each other yet — there is no API contract. See "Current state".

## Running the stack

`docker compose up -d --build` brings up `backend`, `frontend`, `postgres`, `redis`, and
`mailpit` on ports 8000, 3000, 5173, 5432, 8025/1025. See README.md for the port map.

Two consequences worth internalising:

- **`vendor/` and `node_modules/` inside the containers are named volumes, not the host
  directories.** Run backend tooling through `docker compose exec backend …` and frontend
  tooling through `docker compose exec frontend …`. Host-side `vendor/bin/pint`,
  `php artisan test`, and `npx tsc` do not see what the containers use.
- **The entrypoints reinstall on lockfile change, not on every boot.** They md5sum
  `composer.lock` / `package-lock.json` against a stamp inside the dependency volume. Editing
  `composer.json` without running `composer update` will therefore *not* reinstall.

The backend container sets `LARAVEL_SAIL=1` deliberately. `laravel-vite-plugin` keys its
container behaviour off it: Vite binds `0.0.0.0`, takes its port from `VITE_PORT`, and writes
`http://localhost:$VITE_PORT` into `public/hot` so the browser can reach the dev server.
`ServeCommand` also reads it to allow `PHP_CLI_SERVER_WORKERS` without `--no-reload`. This is
why `vite.config.js` needs no changes; don't "clean up" that variable without replacing it.

## Generated instruction files — do not hand-edit

- `backend/AGENTS.md`, `backend/CLAUDE.md` (byte-identical copies), and `backend/.agents/ .claude/
  .cursor/ .zed/` are Laravel Boost output. `boost.json`'s `agents` array lists the targets; contents
  are regenerated by `php artisan boost:update`, which runs automatically on `composer update`
  (`post-update-cmd`). Read them for backend work; change `boost.json` or the skill sources instead of
  the generated copies. `.agents/` and `.claude/` are committed; `.cursor/` and `.zed/` are gitignored.
- `frontend/AGENTS.md` is re-added by `next dev` (see
  `node_modules/next/dist/server/lib/generate-agent-files.js`) and is tracked. Commit it with your work;
  deleting it only recreates the uncommitted change.
- Durable project rules belong in `backend/.ai/rules/` (path-scoped markdown) rather than in this file,
  but only via Boost's `record-rule` MCP tool and only when the user explicitly asks you to record one —
  never on your own initiative. That directory does not exist yet.
- `backend/opencode.json` declares the Boost MCP server (`php artisan boost:mcp`), so it only registers
  for sessions whose working directory is inside `backend/`. There is no root `opencode.json`. Prefer its
  tools over ad-hoc shell/tinker: `database-schema` (call with `summary` first, then per-table filters),
  `database-query`, `search-docs` (scope with `packages`, send several broad topic queries),
  `application-info`, `browser-logs` / `last-error` / `read-log-entries` (recent entries only), and
  `get-absolute-url` (always resolve URLs this way before sharing one with the user).

## Verification order

There is no CI and no pre-commit hooks, so nothing enforces formatting. Run these yourself.

- Backend: `vendor/bin/pint --dirty` → `php artisan test --compact`. No `pint.json`; Pint defaults apply.
- Frontend: `npm run lint` → `npx tsc --noEmit`. There is no `typecheck` script and no frontend test
  runner — no Vitest, no Jest, no `test` script — so `npm test` will not work.
- Pass `--no-interaction` to every Artisan command.
- When working against the Compose stack, prefix the working directory: `docker compose exec
  backend php artisan test --compact`, `docker compose exec frontend npx tsc --noEmit`. Use
  `vendor/bin/pint --test` there, not `--dirty`: only `backend/` is bind-mounted, so the
  container has no Git metadata for `--dirty` to diff against.

## Backend (`cd backend`)

- First-time setup: `composer setup` — installs deps, copies `.env`, generates the key, migrates,
  then `npm install --ignore-scripts` + `npm run build`.
- Dev server: `php artisan dev` (or `composer run dev`) is the unified runner for web + queue + Vite
  + pail, with a TUI. Not `artisan serve`. It comes from `laravel/pao`; `php artisan dev:list` shows
  the four registered processes. Use `--json` for newline-delimited output — it implies `--inline`,
  which is also the default when stdout is not a TTY. Also `--stream`, `--tabs`, `--no-restart`.
- Tests: `php artisan test --compact` or `vendor/bin/pest` — same file-path and `--filter=` args.
  Narrow to the smallest set covering the change, then ask the user to run the full suite. Tests run
  against in-memory SQLite (`phpunit.xml`), so no DB setup is needed.
- `tests/Pest.php` has `RefreshDatabase` **commented out** — uncomment it, or add `uses()` per test,
  before writing Feature tests that hit the database.

### Backend gotchas

- Session, cache, and queue all default to the `database` driver, so `php artisan migrate` is required
  before *any* page loads, not just before storing data.
- `public/build/` is gitignored and produced by `npm run build`. On a fresh clone neither
  `public/build/manifest.json` nor `public/hot` exists, so a bare `@vite` in a new Blade view throws.
  `welcome.blade.php` hides this behind a `file_exists` check that inlines a prebuilt Tailwind
  stylesheet — don't copy that fallback into new views.
- The backend has its own Tailwind pipeline (Vite + `@tailwindcss/vite`, fonts via
  `laravel-vite-plugin/fonts`, `@source` hints in `resources/css/app.css`). It shares nothing with the
  frontend's.
- `database/*.sqlite` is ignored by `backend/database/.gitignore`, so a fresh clone has no DB file
  until `php artisan migrate`.
- `.npmrc` sets `ignore-scripts=true` — pass `--ignore-scripts` to npm installs here.
- `composer.json` requires `php: ^8.3` and the local CLI is 8.4, but the Boost guidelines hardcode
  "PHP 8.4". Stay 8.3-compatible unless you also raise the constraint.
- `artisan dev`, Pint, Pest, and Boost are all `require-dev` — none of them exist in a `--no-dev`
  install, which is why those commands can appear to vanish.

### Backend conventions that differ from older Laravel

- Laravel 13 model attributes, not properties: `#[Fillable([...])]`, `#[Hidden([...])]`. See
  `app/Models/User.php`.
- Route registration is fluent in `bootstrap/app.php`; there is no `routes/api.php` and no auth
  scaffolding (no Breeze/Jetstream/Sanctum). `bootstrap/app.php` registers `web` and `console` only.
- Boost rules apply in `backend/`: use `php artisan make:*` generators, follow sibling-file
  conventions, don't add dependencies or new base directories without approval, and prefer tests over
  verification scripts or tinker.

## Frontend (`cd frontend`)

- `npm run dev` / `build` / `start` / `lint`.
- Next 16.4.2 is not the Next.js in your training data. Bundled docs live at
  `node_modules/next/dist/docs/` — read them before using an API, and mind deprecation notices.
- `next.config.ts` enables `cacheComponents: true` (Cache Components: `use cache`, `cacheLife`,
  static-shell prerendering), `partialPrefetching`, `experimental.agentFeedback`, and Turbopack with
  the `@tailwindcss/turbopack` loader for `*.css`.
- Tailwind v4, CSS-first: `@import "tailwindcss"` and `@theme` in `app/globals.css`, no
  `tailwind.config.js`.
- `PageProps<'/route'>`, `LayoutProps<'/route'>`, and `RouteContext` are globally generated into the
  gitignored `frontend/.next/types/` — don't hand-write prop interfaces for pages and layouts, and
  expect unresolved types until `next dev` or `next build` has run once.
- `tsconfig.json` maps `@/*` to the project root (`./*`), not `./src/*`.

## Current state of the project

The root README is aspirational, not a description of the code. Today there is only the `User` model,
the three default migrations, and a single `/` route; the frontend is still the untouched
`create-next-app` scaffold. Trust the code over the README — in particular its claim about Vitest is
still false. Its `docker-compose.yml` claim is now true.

There is no API contract yet: no API route group, no auth, and no `NEXT_PUBLIC_*` config on either
side. `docker-compose.yml` passes `NEXT_PUBLIC_API_URL` to the frontend container, but nothing reads
it yet. Agree on the API surface before wiring frontend to backend. When you do, the browser at
`localhost:3000` calling `localhost:8000` will need `config/cors.php` published with
`supports_credentials: true` for the cookie session to survive cross-origin requests.
